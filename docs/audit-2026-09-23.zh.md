## 如何使用本文档

- **选取一批。** 从“修复批次”中选一批，或选取单个 ID。在可行时先写一个会失败的
  回归测试，再修复。
- **记录进度。** 更新下方索引中的 Status 列（`open` →
  `fixed <commit>` / `wontfix: reason`）。更新 `docs/handoff.md`。
- **遵守项目规则。** AGENTS.md 依然适用：block 784、只在 main 上开发、不使用
  vLLM、只暂存有意修改的文件、保持中文配套文档同步、绝不放宽容差、停止自己启动的
  GPU 进程。
- **重跑受影响的内容。** 任何对 `kernels.cu` device 代码的修改都需要重跑受影响的
  正式算子用例（REQ-KERNEL-002）。任何热路径修改都需要重新检查相关框架组，之后
  才能声称12组验收仍然成立。

严重级别：

| 级别 | 含义 |

## P0 — 当前即可触发

### SRV-01 单个请求的错误会停止引擎并让所有请求失败

- **位置：**
  - `crates/zmq-worker/src/serving/mod.rs:371-376`：prepare 超时使用 `?`。
  - `mod.rs:482-491`：execute 使用 `.await??`。
  - `mod.rs:463-467`：所有活跃请求都被判为失败。
  - `python/oh_my_vllm/worker/zmq_bridge.py:196-203`：任何异常都变成 `error`。
- **触发：**
  - `temperature=1e-39`。Rust 只检查它是数值
    （`serving/request.rs:401-412`），Python 只检查有限且 ≥ 0
    （`worker/sampling.py:24`）。`sampler.py:80` 做除法后 logits 变为 +inf，softmax
    得到 NaN，随后 `sampler.py:112-113` 抛出异常。
  - 极小的 `repetition_penalty` 以同样方式失败。
  - 违反 grammar（`worker/serving.py:181`）以同样方式失败。
  - 耗时超过 120 s 的 prepare 以同样方式失败。
- **结果：** 所有活跃 stream 以 "worker failed" 失败，此后每个请求都返回 503，直到
  重启。
- **相关：** 步骤中途发生异常后，`worker/model_runner.py:325-368` 可能让部分请求的
  历史和 grammar 状态已被更新。这之所以无害，只是因为 worker 随后会被销毁。
- **修复：**
  - 在 `execute_result` 内报告单请求失败（例如一个 error 字段或
    `finish_reason="error"`），只让该请求失败。
  - 对传输失败和 worker 死亡保留引擎级致命处理。
  - 将 `temperature < 1e-5` 视为 greedy，并在 Rust 和 Python 的校验中都限制
    penalty 的范围。
  - 让每个请求的 step 提交是全有或全无的。
- **验证：**
  - 一个 HTTP 测试：脚本化 worker 返回一个单请求错误，同时另一个 stream 继续运行。
  - 针对极端 temperature 和 penalty 值的 sampler 单元测试。

### SRV-02 Rust 收到 SIGTERM/SIGKILL 后 worker 成为孤儿，继续占用 GPU 和 GPU 锁

- **位置：**
  - `crates/zmq-worker/src/client.rs:76-83`：清理只存在于 `Drop` 中。
  - `client.rs:96-105`：spawn 没有设置父进程死亡信号。
  - `serving/mod.rs:328`：只处理 Ctrl-C。
  - `zmq_bridge.py:118`：`sock.recv()` 没有超时。
- **触发：** `kill`、`timeout` 或 OOM killer 终止 Rust 进程。
- **结果：**
  - Python 在持有权重和 KV cache 的状态下永远阻塞。
  - `scripts/with-gpu.sh:26-27` 会把它的 flock fd 传给子进程，因此孤儿进程也持有
    GPU 锁，之后的 `with-gpu.sh` 运行会一直等待该 GPU。
  - 这违反了 AGENTS.md 的 GPU 清理规则。
- **修复：**
  - 在 `pre_exec` hook 中调用 `prctl(PR_SET_PDEATHSIG, SIGKILL)`，并附
    `// SAFETY:` 注释。
  - 像处理 Ctrl-C 一样处理 SIGTERM。
  - 增加 Python 侧的父进程看门狗（检测 `os.getppid()` 变化，或使用接收超时加存活
    检查）。
- **验证：** 用脚本化 CPU worker 启动 `serve`，对 Rust 进程发送 SIGKILL，并断言
  worker 在限定时间内退出。

### SRV-03 容量错误和内部错误以 HTTP 400 返回

- **位置：**
  - `serving/mod.rs:365-367`：活跃数上限拒绝。
  - `mod.rs:220`：每个 `ready` 错误都变成 400。
  - `mod.rs:173`：Axum `JsonRejection` 的 413/415 被改写为 400。
- **结果：** OpenAI SDK 客户端和 OMP 会重试 429/503，但不会重试 400。负载尖峰以及
  tokenizer 或 CUDA 错误等内部失败都变成了硬性的客户端错误。
- **修复：** 在 `ready` 结果中携带错误类别：
  - 容量问题返回 429 或 503
  - 校验失败返回 400
  - 内部失败返回 500
  - Axum rejection 使用 `rejection.status()`
- **验证：** 针对第65个并发请求、过大的请求体和 worker prepare 异常的 HTTP 测试。

### SRV-04 因长度结束时丢弃被暂扣的 reasoning/content 字节

- **位置：**
  - `serving/mod.rs:573-575`：`feed(&text, reason == Some("stop"))`。
  - `serving/parser.rs:47-51` 和 `:80-86`：`safe_prefix` 会暂扣可能构成标记前缀的
    内容。
- **触发：** `max_tokens` 耗尽时 reasoning 恰好以 `</think>` 的前缀结尾，或者启用
  tool 时 content 恰好以 `<tool_call>` 的前缀结尾。
- **结果：** 这些末尾字节永远不会到达 stream 或最终响应。
- **修复：**
  - 在所有终止原因下都 flush `pending`。
  - 对 `length`，只丢弃从未完成的 `<tool_call>` 开始的文本，这正是文档中说明的
    意图。
- **验证：** parser 单元测试，覆盖以每种标记前缀结尾的 length 结束情况。

### SCH-01 `update()` 信任 worker 输出；可能 panic、下溢或停滞

- **位置：**
  - `crates/scheduler/src/lib.rs:322-340`：serving 路径上的 `assert!`；
    `num_computed_tokens` 由接受数量推导，而 `token_ids` 来自输出。
  - `lib.rs:153`：`num_tokens_with_spec() - num_computed_tokens`。
  - `lib.rs:310-311`：doc 注释称 `update()` 在不匹配时 panic；代码实际是
    `continue`。
  - release profile（`Cargo.toml:33-37`）没有启用溢出检查，因此下溢会回绕。
- **场景：**
  - 多报的接受数量会让引擎 panic。
  - `accepted=3` 但只返回一个 token 时，`num_computed_tokens` 会超前于历史。若没有
    安装新的 draft，第153行下溢，该请求过量分配 page 并得到空的 token 列表；若有
    新的 draft，则会调度错误的 draft 切片。
  - 对于未完成的 decode，空的 `token_ids` 会让请求一直得不到调度，直到超时。
- **修复：**
  - 让 `update()` 返回 `Result`。
  - 在修改任何状态之前，对完成的 step 校验 `token_ids.len() == accepted + 1`，对
    部分 prefill 校验为 `0`。
  - 保留 `num_computed_tokens <= token_ids.len()` 的硬检查。
- **验证：** 使用畸形 worker 输出的 Rust 测试。

### SCH-02 引用计数/空闲链表保护仅在 debug 下生效

- **验证：** 一个测试，证明在类 release 配置下重复释放会 panic。

### SCH-03 起点未对齐时 `aligned_prefill` 可能永远返回0

### SCH-04 超出池容量的请求没有被拒绝

### SCH-05 `remove_blocks_in_range` 在第一个 null 处停止

- **位置：** `crates/kv-cache/src/group.rs:519-525`（遇到 `NULL_BLOCK_ID` 时
  `break`）。speculative 迁移（`group.rs:391-398`）会在旧 state slot 之上留下

- **当前行为：** 安全，因为此类空洞之下唯一的 block 会在一步之后通过

- **风险：** 任何让空洞之下存在第二个活跃 block 的改动，都会让该 block 一直被占用

- **验证：** 一个在空洞之下有两个活跃 block 的 coordinator 测试。

### SRV-05 RPC 超时不具备取消安全性；回复无法匹配

- **位置：**
  - `crates/zmq-worker/src/client.rs:255-257`：先发送，再接收。
  - `client.rs:343-347`。
  - Python 不回显 `step_id`（`zmq_bridge.py:179-183`），Rust 也不检查它。
- **当前行为：** 安全，因为两种超时都是致命的（SRV-01）。
- **风险：** 如果超时变为可恢复，下一次调用会读到上一次的回复，把一个 step 的
  token 应用到错误的 batch 上。
- **修复：**
  - 回显 `step_id`，prepare 则回显 `request_id`。
  - 拒绝不匹配的回复，或在任何 RPC 被取消后把客户端标记为 poisoned。
- **验证：** 一个 CPU 测试，脚本化 worker 延迟一次回复。

### SRV-06 无回复消息的错误会杀死 worker；重复 prepare 会删除活跃请求

- **位置：**
  - `zmq_bridge.py:156-162`：`register` 没有 `try`。

  - `crates/zmq-worker/src/main.rs:111-131`：`--prompt-file` 不检查 token ID 是否

  - `worker/serving.py:318`：`prepare` 在重复检查抛出异常之前就覆盖了
    `generations[rid]`。随后它的 `except` 会注销该活跃请求。
- **结果：**
  - `run --prompt-file` 中的无效 token ID 会让 worker 退出。Rust 只报告

  - 重复 ID 会破坏一个活跃请求。
- **修复：**
  - 在无回复的处理函数中捕获异常，并在下一次回复中报告。
  - 在 Rust 中校验 token 范围。
  - 在修改状态之前检查重复。
- **验证：** 针对无效 register 和重复 prepare 的 bridge 测试。

### SRV-07 `serving_outputs` 旁路通道每步被覆盖

- **位置：**
  - `client.rs:72`、`:267-277`：一个公开 map 每步被替换。

- **当前行为：** 安全，因为每次 `execute` 的结果都会被立即取走。
- **风险：** 在取走之前发生第二次 `execute`（例如 `mod.rs:509` 的空闲分支）会丢失

- **修复：** 在 `WorkerOutput` 或 serving 输出类型中返回这些字段。

## P2 — 性能与健壮性

### PY-03 32个 graph 的预算：先到先得、无淘汰、key 依赖接受数量

- **位置：**
  - `worker/model_runner.py:207-215`
  - `worker/mtp.py:66-68`、`:116`
- **key 如何倍增：**
  - draft key 包含 token 总数，而它取决于接受数量（每个请求1..5）。
  - 在 bs=4、batch 逐渐缩小且有多种 extent 时，key 数量会超过32。
  - extent 以4096为步长，因此仅 262k 上下文就有64种 extent。
- **结果：**
  - 预算用尽后，新形状以 eager 方式运行并增加 host 同步。
  - 在服务过程中捕获新形状会同步整个 batch。
  - 在长期运行的服务器中，后续工作负载会发现预算已被用完。
- **修复：**
  - 将每个请求的 draft query 填充到5个 token，被跳过的写入使用负 slot。
  - extent 按2的幂分桶。
  - 增加 LRU 淘汰。
  - 预先捕获预期的形状。

### PY-04 每个 CUDA graph 独占私有内存池，且在确定 cache 大小之后才捕获

- **位置：** `worker/decode_graph.py:145`、`:190`、`:245`。没有使用
  `graph_pool_handle()`。
- **结果：** 最多64个 graph 各自保留自己的中间结果，其中包括约 20 MB 的 FP32
  logits。在 cache 接近满时后期出现的新形状可能在捕获期间 OOM，进而触发 SRV-01。
- **修复：**
  - 共享一个内存池；replay 从不重叠，且输出都会被消费或复制。
  - 在确定 cache 大小之前捕获预期的形状。

### PY-05 MTP 元数据按 `max_model_len` 分配大小，并按每个 token 行重复

- **位置：**
  - `worker/mtp.py:69-78`、`:118-123`
  - `worker/model_runner.py:257-266`
- **结果：** 在 `max_model_len=262144` 时，即使输入只有 32k，宽度也是335个 page。
  在 bs=4 且启用 MTP 时，每步要构建并上传约 8k 个 Python 整数。
- **修复：**
  - 像 target 路径那样按 extent 分配大小。
  - 每个请求上传一行，在 device 上展开。
- **验证：** 测量 MTP 各组；它们的余量最小（bs4 时为97.52%）。

### PY-06 每步围绕 host 同步完全串行化

- **位置：**
  - `worker/sampler.py:104`：每步一次批量的 greedy 传输（固有开销）。
  - `worker/sampler.py:170`：每个非 greedy 请求多一次 `.tolist()`。
  - `worker/mtp.py:130`、`:204`、`:228`：回退路径再增加3次同步。
  - `worker/tensors.py:16`：pageable 的 H2D 拷贝。
- **结果：** host 规划、msgpack/ZMQ 和 Rust 调度从不与 GPU 工作重叠。
- **修复：**
  - 批量处理非 greedy 的传输。
  - 使用持久化的 pinned 暂存区。
  - 在 GPU 运行时规划下一步。
- **注意：** 此前的 profiling 发现约 11 ms 的 `target_greedy_to_cpu` 区间主要是在等待
  GPU，而非 CPU 或 ZMQ 工作，也没有证实 Rust 调度/ZMQ 是瓶颈。Draft-KV NHD→head-major
  以及量化 warp 数扫描都没有带来收益。参见
  `bench/baseline/2026-09-22-performance-gap.json` 中的 `limitations`/`controls`；修改前后
  都要测量。

### PY-07 penalty 每步都做逐 prompt 的工作；top-p 对完整词表排序

- **位置：** `worker/sampler.py:37`、`:44-51`、`:85`。
- **结果：**
  - 只要有任何 penalty，每步都要在 Python 中遍历整个 prompt 并运行 `bincount`，
    粗略估计在 262k token 时为 10+ ms。
  - 即使在 top-k 之后，top-p 仍对248,320个条目排序。
- **修复：**
  - 在注册时于 device 上一次性计算 prompt 计数，并在提交时更新生成计数。
  - 只对 top-k 留下的候选排序。

### SRV-08 请求准备在 step 循环中内联执行

- **位置：** `serving/mod.rs:514-516` → `admit` → `prepare_request`。
- **结果：** 大 prompt 的模板渲染、分词和 grammar 编译会让所有活跃 stream 暂停。
- **修复：** 在单独的 Python 线程或进程中执行 prepare，或将 prepare 与 execute

### SRV-09 tool-call 解析在引擎线程上为 O(n²)

- **位置：** `serving/parser.rs:63-69`、`:138-173`、`:187-195`。每步都会重新扫描并
  重新解析整个待处理的调用。
- **修复：** 保存解析器进度（当前参数和字节偏移）。

### SRV-10 256事件的 stream 缓冲按 step 计数，而不是按时间

- **位置：** `serving/mod.rs:202`、`:337-346`。这在 `serving.md` 中有记录。
- **结果：** 暂停约256个 step 的客户端会丢失其请求。
- **修复：** 增加基于时间的宽限期。

### SCH-06 抢占驱逐的是失败的请求，而不是最低优先级的请求

- **位置：** `crates/scheduler/src/lib.rs:206-217`。模块文档（`lib.rs:13-14`）和
  REQ-FUNC-004 描述的是另一种策略。多个被驱逐者以逆优先级顺序通过 `push_front`

- **结果：** 在内存压力下，较早的请求会丢失进度。这对 benchmark 没有影响，因为
  benchmark 要求零抢占。
- **修复：**
  - 从 running 队列尾部抢占，并重试当前请求。
  - 按优先级顺序重新入队。
  - 然后更新需求和设计文本使之一致。

### SCH-07 每填满一个 block 就重新哈希全部历史

- **位置：** `crates/scheduler/src/lib.rs:343-346`。
- **结果：** 在 262k token 时，每个请求每784个 token 出现一次约 0.5–1 ms 的

- **修复：** 只哈希新的 block，并从上一个哈希链式衔接。

### KRN-06 流式存储的 `"memory"` clobber 限制了 load 提前

- **位置：** `kernels.cu:260-261`（`asm volatile("st.global.cs...": "memory")`）。

### KRN-07 未对齐时 decode 静默克隆整个 FA cache

- **位置：** `kernels/decode_attention.py:63-66`。
- **结果：** 未对齐的 cache view 每层每步复制约 4 GiB。生产 cache 是对齐的，因此

### KRN-08 快速/通用变体的选择不可观测

## 撤回或更正的第一轮结论

同一会话中较早的一轮审阅提出了一些 CUDA 相关结论，但独立的第二轮审阅并不支持。
不要按原始表述据此采取行动。

| 结论 | 判定 | 理由 |
|---|---|---|
| `rms()` 把 `out` 别名为 residual 缓冲区 | 驳回 | 参数为 `(x, residual, weight, out, summed, ...)`，因此 `out` 就是 `summed`。在 `Residual=false` 时两者都不会被读写（`kernels.cu:283`、`:301`）。 |
| quantize 分派混淆了 FP16 与 BF16 | 驳回 | `kernels.cu:176` 首先检测 `kDLBfloat`。真正残留的问题是兜底的 `float` 分支（MNT-02）。 |
| 单次 FMA 的倒数修正破坏 FP8 舍入 | 驳回，但依赖一个假设 | 82,048个精确用例与 `__fdiv_rn` 逐位一致，前提是 `rcp.approx` 误差 ≤ 1 ulp。仅凭源码无法验证这一点。 |
| `__fdividef` 在 gate sigmoid 中损失精度 | 驳回 | 分母位于 (1,2]，因此误差 ≤ 2 ulp，低于 BF16 输入的分辨率。 |
| `compiled()` cache 没有 key | 已由 EVD-12 整改解决 | TVM FFI key 包含源码/参数，自定义编译 flag 加入 nvcc 路径/版本；sidecar 为离线复用绑定其余构建身份。 |
| `"memory"` clobber 损害寄存器分配 | 机制已更正 | 它实际限制的是 load 提前（KRN-06）。 |
