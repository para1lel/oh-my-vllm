# ADR-014: 长 prefill 预算分配

日期: 2026-10-12. 状态: 实现进入验收.

## 问题

源码 `22dd754` 的 MTP4 输入 `131072`, 输出 `4096`, batch `4` decode 时延未通过.
墙钟中位数为 `39.9496` 秒, 下界为 `12.2634` 秒.
倍率为 `3.2576`, 高于保持不变的 `3` 倍上限.
Prefill 倍率与两个离散度检查均通过.

第一条请求比最后一条提前约 `19.7` 秒开始 decode.
它的 decode 区间包括十二个混合 step, 其中包含其它请求的长 prefill.
CUDA Event 测量也显示该区间. 它们可能包含主机提交间隙, 不能提供纯 kernel 时间.
原始完整测量组保留失败状态. 取消的采集不能提供验收结论.

## 决定

持续 prefill 分配前, 先为活动 decode 输入预留额度.
至少两条符合条件的长 prefill 共享剩余 token 预算.
保持 FIFO 准入, 并从队尾优先抢占后准入请求.
每个首 token 在实际完成时发布, 不另设输出延迟.

长 prefill 根据准入时的未命中区间分类, 先以只读方式查询前缀.
该区间必须超过配置中的每轮预算.
`Request.prefill_start` 保留最初的复用位置, 直到本次 prefill 完成.
抢占时重置它. 重新准入使用新验证的前缀命中.
当剩余区间缩短到一轮以内时, 该分类仍然有效.

暂停请求与可用 sequence slot 之外的请求不计入共享数.
每个参与请求至少要能得到一个完整 block.
每条额度向下对齐到 `784` 的倍数.
预算为 `32768` 时, 两条不复用前缀的长请求各得到 `15680` 个 token.
四条各得到 `7840`, 总计 `31360` 个 token.
提示词尾段, checkpoint 边界与小于一个 block 的前进继续遵守原规则.

短提示词使用普通预算路径.
缓存提示词的初始未命中区间不超过配置中的每轮预算时, 也使用该路径.
前缀估算不跨越分配过程保存命中向量.
准入重新查询, 然后执行原有双 pool 保护与分配顺序.

## 验证

CPU 测试检查四条请求持续推进, 真实 `784` 边界, 提示词尾段, decode 预留, 前缀命中与暂停后的 sequence 限制.
回归用例在 running 队列中, 将短 prefill 尾段放在活动 decode 前面.
每条 prefill 都必须遵守该 decode 的输入预留预算.

保留原有全部 `317` 个算子用例与固定的 TileLang 对比.
为新的合法形状与实现路径添加静态推导的长 MTP 和多 prefill 用例.
继续使用完整输出, 状态, 三轮, 每轮二十配对与置信界门槛.

重新测试十五项阶段负载, 六项完整 context 用例, reasoning 预算与两种持久 OMP 模式.
新的 ragged 形状, 图捕获存储, 数值结果与资源增长需要新证据.
此前源码的结果保留原始身份与限制.
数值容差, DSpark 权重, 理论公式与验收上限保持不变.
