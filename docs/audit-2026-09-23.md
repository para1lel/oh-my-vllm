# Code audit — 2026-09-23

Status: **in progress**. Audited commit: `030f60f` (clean `main`). Line numbers below refer
to that commit; re-locate them with the quoted symbol if code has moved.

## Scope and method

The audit covered every project-owned source file: `crates/`, `python/`,
`tests/`, `benchmarks/`, `scripts/` and `development/`. Frozen artifact JSON was
not reviewed line by line. Six independent reviews ran in parallel:

- Rust scheduler and KV cache
- Rust serving and ZMQ client
- Python worker and model
- Kernel wrappers and the frozen TileLang reference
- An independent second pass over `kernels.cu`
- Tests, benchmarks and scripts

Review was read-only. No GPU run, compilation or fix was part of the audit. The
main agent re-read the cited code for every P0 finding and most P1 findings. A
second CUDA reviewer tested the numerical claims with CPU exact-arithmetic
simulations, outside the repository.

**Overall result at audited `030f60f`.** With the then-current defaults and
benchmark workloads, the audit found no defect that produces wrong tokens.
It did not invalidate the 12-row performance and correctness evidence for
clean `c36d1c9`; that evidence is historical and does not verify the current
source after remediation. The artifacts were
produced by `benchmarks/ttft.py`, which enforces warmup, repetition and spread
gates, and their embedded baseline hashes reproduce. At that time its steady-state
audit did not cover the CUDA kernel cache (EVD-13, since repaired). The problems fall into
three groups:

- **Serving availability.** One bad request can stop the whole engine.
- **Latent silent-wrong contracts.** Safety depends on a distant caller rather
  than a check at the call site.
- **Evidence gaps.** Some guarantees are stated in prose but not enforced in
  code.

## How to use this document

- **Take a batch.** Pick a batch from "Remediation batches" or a single ID. Write
  a failing regression test first where one is practical, then fix.
- **Record progress.** Update the Status column in the index below (`open` →
  `fixed <commit>` / `wontfix: reason`). Update `docs/handoff.md`.
- **Follow the project rules.** AGENTS.md still applies: block 784, main only, no
  vLLM, stage only intended files, keep Chinese companions in sync, never relax
  tolerances, and stop owned GPU processes.
- **Re-run what a change affects.** Any change to `kernels.cu` device code
  requires re-running the affected formal operator cases (REQ-KERNEL-002). Any
  hot-path change requires re-checking the relevant framework rows before claiming
  that 12-row acceptance still holds.

## P0 — reachable today

### SRV-01 One request's error stops the engine and fails every request

- **Where:**
  - `crates/zmq-worker/src/serving/mod.rs:371-376`: the prepare timeout is `?`.
  - `mod.rs:482-491`: execute uses `.await??`.
  - `mod.rs:463-467`: every active request is failed.
  - `python/oh_my_vllm/worker/zmq_bridge.py:196-203`: any exception becomes `error`.
- **Trigger:**
  - `temperature=1e-39`. Rust only checks that it is numeric
    (`serving/request.rs:401-412`), and Python only checks finite and ≥ 0
    (`worker/sampling.py:24`). `sampler.py:80` divides the logits to +inf, softmax
    gives NaN, and `sampler.py:112-113` raises.
  - A tiny `repetition_penalty` fails the same way.
  - A grammar violation (`worker/serving.py:181`) fails the same way.
  - A prepare that takes longer than 120 s fails the same way.
- **Result:** all active streams fail with "worker failed", and every later
  request gets 503 until restart.
- **Related:** `worker/model_runner.py:325-368` can leave some requests with
  updated histories and grammar state after a mid-step exception. This is
  harmless only because the worker is torn down afterwards.
- **Fix:**
  - Report per-request failures inside `execute_result` (for example an error
    field or `finish_reason="error"`) and fail only that request.
  - Keep engine-fatal handling for transport failures and worker death.
  - Treat `temperature < 1e-5` as greedy, and bound penalties in both Rust and
    Python validation.
  - Make step commit all-or-nothing per request.
- **Verify:**
  - An HTTP test with the scripted worker returning one per-request error, while
    another stream continues.
  - Sampler unit tests for extreme temperature and penalty values.

### SRV-02 Worker orphaned on Rust SIGTERM/SIGKILL keeps GPU and GPU lock

- **Where:**
  - `crates/zmq-worker/src/client.rs:76-83`: cleanup exists only in `Drop`.
  - `client.rs:96-105`: the spawn has no parent-death signal.
  - `serving/mod.rs:328`: only Ctrl-C is handled.
  - `zmq_bridge.py:118`: `sock.recv()` has no timeout.
- **Trigger:** `kill`, `timeout` or the OOM killer stops the Rust process.
- **Result:**
  - Python blocks forever while holding the weights and KV cache.
  - `scripts/with-gpu.sh:26-27` passes its flock fd to children, so the orphan
    also holds the GPU lock and later `with-gpu.sh` runs wait on that GPU.
  - This breaks the AGENTS.md GPU cleanup rule.
- **Fix:**
  - `prctl(PR_SET_PDEATHSIG, SIGKILL)` in a `pre_exec` hook, with a `// SAFETY:`
    comment.
  - Handle SIGTERM like Ctrl-C.
  - Add a Python-side parent watchdog (`os.getppid()` change, or a receive
    timeout plus a liveness check).
- **Verify:** start `serve` with the scripted CPU worker, SIGKILL the Rust
  process, and assert the worker exits within a bound.

### SRV-03 Capacity and internal errors returned as HTTP 400

- **Where:**
  - `serving/mod.rs:365-367`: the active-limit rejection.
  - `mod.rs:220`: every `ready` error becomes 400.
  - `mod.rs:173`: Axum `JsonRejection` 413/415 are rewritten to 400.
- **Result:** OpenAI SDK clients and OMP retry 429/503 but not 400. Load spikes
  and internal failures such as tokenizer or CUDA errors become hard client
  errors.
- **Fix:** carry an error kind with the `ready` result:
  - 429 or 503 for capacity
  - 400 for validation
  - 500 for internal failures
  - `rejection.status()` for Axum rejections
- **Verify:** HTTP tests for the 65th concurrent request, an oversized body and
  a worker prepare exception.

### SRV-04 Length finish drops held-back reasoning/content bytes

- **Where:**
  - `serving/mod.rs:573-575`: `feed(&text, reason == Some("stop"))`.
  - `serving/parser.rs:47-51` and `:80-86`: `safe_prefix` holds back possible
    marker prefixes.
- **Trigger:** `max_tokens` is exhausted while reasoning ends in a prefix of
  `</think>`, or while enabled-tool content ends in a prefix of `<tool_call>`.
- **Result:** those final bytes never reach the stream or the final response.
- **Fix:**
  - Flush `pending` on every terminal reason.
  - For `length`, drop only text starting at an unfinished `<tool_call>`, which
    is the documented intent.
- **Verify:** parser unit tests for length finishes that end in each marker
  prefix.

### KRN-01 Grouped decode grid hard-codes at most 5 query rows per group

- **Where:**
  - `python/oh_my_vllm/kernels/cuda_backend/kernels.cu:1410`:
    `tiles = ((grouped ? 5 : 1) * (h / hk) + bq - 1) / bq`.
  - `kernels/decode_attention.py:88-92`: `query_tile` has the same assumption.
- **Existing guards:** they are separate and upstream only:
  - `worker/model_runner.py:34`
  - `worker/batch_plan.py:68, 74`
  - `worker/decode_graph.py:63` (`max_q_len=5`)
  - `kernels/mtp_attention.py:39`
- **Trigger:** a group with 6 or more rows, for example more speculative tokens.
- **Result:** rows are never computed. `partial`/`lse` come from `torch.empty`,
  so the merge reads uninitialized memory and returns garbage or NaN without an
  error. Both backends are affected.
- **Fix:**
  - Pass the maximum group size from the host and `TVM_FFI_ICHECK` it.
  - Derive `tiles` and `query_tile` from it.
  - Assert it in `decode()`.
- **Verify:** a wrapper test showing that a 6-row group raises.

### KRN-02 Out-of-range KV slots skipped silently or written out of bounds

- **Where:**
  - `kernels.cu:555`: `prepare_attention` returns on `slot >= capacity`, so the
    KV write is silently dropped.
  - `kernels.cu:967-970`: `append_kernel` checks only `slot < 0`, so it writes
    out of bounds.
  - `tilelang_reference/attention.py:23`: the frozen TileLang chain writes out of
    bounds.
  - No wrapper bounds-checks slots, read/write slots, sequence IDs or tables.
- **Trigger:** misconfigured FA capacity, or a Rust or worker bug.
- **Result:** stale KV and wrong attention output, or corrupted memory. The
  backends disagree on the same input.
- **Fix:**
  - Treat an out-of-range slot as an error: a device error flag checked after
    the call, or `__trap()`.
  - Add the upper bound to `append`.
  - Document the trust boundary in each wrapper.
- **Verify:** tests showing that an out-of-range slot raises on both entries.

### KRN-03 Attention merge yields NaN when every split of a row is empty

- **Where:**
  - `kernels.cu:1465-1471`: `maximum=-inf`, then `log - maximum` is NaN, and the
    output is `accum/total`.
  - `kernels.cu:1313`: the partial kernel guards the same case with `safe`.
- **Reachability:** today every row has `length > first`. MTP lengths are at
  least 2, and the Python reviewer found no padded graph rows. The case is
  reachable if an empty row is ever scheduled.
- **Fix:**
  - Use `maximum == -INFINITY ? 0 : maximum`.
  - Guard `total > 0` and write zeros for an empty row.
- **Verify:** a merge test with all-empty splits.

### KRN-04 int32 flat offsets in FP8 quantize and SiLU

**Current correction (`952a01d` and `312c54b`, independently reviewed):** The original
`eb5ff62` wrapper guard prevented offset overflow, but counted the already
packed fused SiLU input width twice. EVD-09's output gate exposed a false
rejection at the first large formal `silu_quant` case (32144 × 34816 input).
The corrected wrapper and direct CUDA FFI guard use the true input element
count, allow exactly `2**31` elements (largest offset `2**31 - 1`), and reject
larger inputs before launch. Division-based checks avoid host overflow; the
kernel's int width is separately bounded. `312c54b` applies the same exact
boundary to the standalone `silu_mul` Python wrapper and direct CUDA FFI,
which the packed-path fix had not covered. CPU tests cover below/at/above the
limit, the formal shape, and fused versus plain width. B200 direct FFI
contracts passed 55/55, including >`2**31` no-launch cases and valid SiLU
output. On clean `312c54b`, all 60 selected formal `quant`/`silu_quant`/
`gates`/`recurrent` cases passed on UUID
`GPU-a832d9c1-260f-9e37-0c99-95e62ab16ca5` with output verification,
3 × 20 alternating pairs, and positive one-sided 95% bootstrap bounds;
the smallest lower bound was 0.00000699734 ms. A separate gates run on UUID
`GPU-80cebbaf-a106-2605-b902-f5f9a08645ea` passed 13/13 with a
0.0000465867 ms lower bound for the previously failed gates shape. The first
clean `312c54b` run passed 59/60 because that gates case missed its bound;
both backends showed elevated timing and the cause remains unconfirmed, so
that attempt is rejected diagnostic evidence. The first clean `6bd2119`
attempt stopped at the packed-path false rejection and is also not acceptance
evidence. The complete 147-case matrix and 12 framework rows remain pending.

- **Where:**
  - `kernels.cu:45`: `int offset = row * width * (Silu ? 2 : 1) + ...`.
  - `kernels.cu:102`: the output index.
  - `kernels.cu:189`, `:196`: the same pattern in SiLU.
  - Neither wrapper (`kernels/fp8.py`, `kernels/elementwise.py`) checks the row
    limit.
- **Limit:**
  - The fused SiLU path at width 17408 overflows from 61,681 rows. The plain path
    overflows from 123,362 rows.
  - The current per-step budget is 32,768 tokens (`crates/scheduler/src/lib.rs:47`),
    about 53% of the int32 range.
- **Fix:** use 64-bit offsets, or reject `rows * input_width > 2**31` in the
  wrappers.
- **Verify:** a wrapper test at the limit using a small width.

### KRN-05 Public `gdn.normalize_qk` validates nothing

- **Where:**

### PY-01 FA page writes are not checked for cross-request sharing

- **Where:** `worker/batch_plan.py:115-135`. `validate_batch` checks recurrent
  slots only. `model_runner.py:198-201` and `mtp.py:150` write FA slots and
  `boundary_hidden`.
- **Trigger:** a Rust refcount or prefix-cache bug hands out a shared page as a
  writable tail.
- **Result:** Python silently overwrites another request's KV and the cached
  prefix. This also contradicts architecture.md, which states that Python
  validates physical addresses.
- **Fix:** require the pages touched by `fa_slots` to be disjoint across
  requests in the batch.
- **Verify:** a `test_batch_plan.py` case with two requests writing the same page.

### PY-02 FP8 projection packing ignores 128-row scale-block alignment

- **Where:** `models/qwen.py:46-58`. `torch.cat` joins weights and block scales.
  The only check rejects mixed quantized and unquantized parts.
- **Trigger:** a checkpoint that quantizes `in_proj_a` and `in_proj_b` (48 rows
  each).
- **Result:** rows 48–95 use the wrong scale, silently corrupting decay and beta.
- **Fix:** assert `w.shape[0] % 128 == 0` for every scaled part.
- **Verify:** a loader unit test with a synthetic 48-row scaled part.

### SCH-01 `update()` trusts worker output; panic, underflow or stall

- **Where:**
  - `crates/scheduler/src/lib.rs:322-340`: a serving-path `assert!`, and
    `num_computed_tokens` is derived from the accepted count while `token_ids`
    comes from the output.
  - `lib.rs:153`: `num_tokens_with_spec() - num_computed_tokens`.
  - `lib.rs:310-311`: the doc comment says `update()` panics on a mismatch; the
    code `continue`s.
  - The release profile (`Cargo.toml:33-37`) does not enable overflow checks, so
    underflow wraps.
- **Scenarios:**
  - An over-reported accepted count panics the engine.
  - `accepted=3` with one returned token leaves `num_computed_tokens` ahead of
    the history. If no new drafts are installed, line 153 underflows and the
    request over-allocates pages with an empty token list; with new drafts it
    schedules a wrong draft slice instead.
  - An empty `token_ids` for an unfinished decode leaves the request unscheduled
    until timeout.
- **Fix:**
  - Return `Result` from `update()`.
  - Validate `token_ids.len() == accepted + 1` for a completed step, and `0` for
    a partial prefill, before changing any state.
  - Keep a hard check that `num_computed_tokens <= token_ids.len()`.
- **Verify:** Rust tests with malformed worker outputs.

### SCH-02 Refcount/free-list guards are debug-only

- **Where:** these checks are `debug_assert!`:

### SCH-03 `aligned_prefill` can return 0 forever for an unaligned start

- **Where:** `crates/scheduler/src/lib.rs:84-87`. Rounding down happens before
  the `next_boundary` stop. `lib.rs:159-161` keeps a request that got 0 tokens.

- **Verify:** a scheduler test with an unaligned `num_computed_tokens`.

### SCH-04 Requests larger than pool capacity are not rejected

- **Where:**

### SCH-05 `remove_blocks_in_range` stops at the first null

- **Where:** `crates/kv-cache/src/group.rs:519-525` (`break` on `NULL_BLOCK_ID`).

### SRV-05 RPC timeouts are not cancellation-safe; replies are unmatched

- **Where:**
  - `crates/zmq-worker/src/client.rs:255-257`: send, then receive.
  - `client.rs:343-347`.

### SRV-06 Fire-and-forget message errors kill the worker; duplicate prepare deletes a live request

### SRV-07 `serving_outputs` side channel is overwritten every step

## P2 — performance and robustness

### PY-03 32-graph budget: first come first served, no eviction, acceptance-dependent keys

- **Where:**
  - `worker/model_runner.py:207-215`
  - `worker/mtp.py:66-68`, `:116`
- **How keys multiply:**
  - Draft keys include the token total, which depends on the accepted count
    (1..5 per request).
  - At bs=4 with shrinking batches and several extents, this exceeds 32 keys.
  - Extents step by 4096, so 262k context alone has 64 extents.
- **Result:**
  - After the budget is spent, new shapes run eagerly and add host syncs.
  - Capturing a new shape mid-service synchronizes the whole batch.
  - In a long-lived server, later workloads find the budget already used.
- **Fix:**
  - Pad draft queries to 5 tokens per request, using negative slots for skipped
    writes.
  - Bucket extents by powers of two.
  - Add LRU eviction.
  - Pre-capture the expected shapes.

### PY-04 Each CUDA graph owns a private pool and is captured after cache sizing

- **Where:** `worker/decode_graph.py:145`, `:190`, `:245`. There is no
  `graph_pool_handle()`.
- **Result:** up to 64 graphs each keep their own intermediates, including about
  20 MB of FP32 logits. A late new shape near a full cache can OOM during
  capture, which then triggers SRV-01.
- **Fix:**
  - Share one pool; replays never overlap, and outputs are consumed or copied.
  - Capture expected shapes before sizing the cache.

### PY-05 MTP metadata sized by `max_model_len` and repeated per token row

- **Where:**
  - `worker/mtp.py:69-78`, `:118-123`
  - `worker/model_runner.py:257-266`
- **Result:** at `max_model_len=262144` the width is 335 pages even at 32k input.
  At bs=4 with MTP, each step builds and uploads about 8k Python integers.
- **Fix:**
  - Size by extent, as the target path does.
  - Upload one row per request and expand it on the device.
- **Verify:** measure the MTP rows; they have the smallest margin (97.52% at bs4).

### PY-06 Step fully serialized around host syncs

- **Where:**
  - `worker/sampler.py:104`: the one batched greedy transfer per step (inherent).
  - `worker/sampler.py:170`: one extra `.tolist()` per non-greedy request.
  - `worker/mtp.py:130`, `:204`, `:228`: the fallback path adds 3 more syncs.
  - `worker/tensors.py:16`: pageable H2D copies.
- **Result:** host planning, msgpack/ZMQ and Rust scheduling never overlap GPU
  work.
- **Fix:**
  - Batch non-greedy transfers.
  - Use persistent pinned staging.
  - Plan the next step while the GPU runs.
- **Caution:** earlier profiling found the ~11 ms `target_greedy_to_cpu` span is
  mostly waiting for the GPU, not CPU or ZMQ work, and did not establish Rust
  scheduling/ZMQ as a bottleneck. Draft-KV NHD→head-major and quantization
  warp-count scans gave no gain. See `limitations`/`controls` in
  `bench/baseline/2026-09-22-performance-gap.json`; measure before and after.

### PY-07 Penalties do per-prompt work every step; top-p sorts the full vocabulary

- **Where:** `worker/sampler.py:37`, `:44-51`, `:85`.
- **Result:**
  - With any penalty, each step iterates the whole prompt in Python and runs
    `bincount`, rough estimate 10+ ms at 262k tokens.
  - Top-p sorts 248,320 entries even after top-k.
- **Fix:**
  - Compute prompt counts on the device once at registration, and update
    generated counts on commit.
  - Sort only the top-k survivors.

### SRV-08 Request preparation runs inline in the step loop

- **Where:** `serving/mod.rs:514-516` → `admit` → `prepare_request`.
- **Result:** template rendering, tokenization and grammar compilation for a
  large prompt pause every active stream.
- **Fix:** prepare in a separate Python thread or process, or pipeline prepare

### SRV-09 Tool-call parsing is O(n²) on the engine thread

- **Where:** `serving/parser.rs:63-69`, `:138-173`, `:187-195`. The whole pending
  call is re-scanned and re-parsed each step.

### SRV-10 256-event stream buffer is counted in steps, not time

- **Where:** `serving/mod.rs:202`, `:337-346`. This is documented in `serving.md`.

### SCH-06 Preemption evicts the failing request, not the lowest priority

- **Where:** `crates/scheduler/src/lib.rs:206-217`. The module doc

- **Fix:**

### KRN-09 Launch errors checked, execution errors attributed late

## Retracted or corrected first-pass claims

An earlier pass in the same session made CUDA claims that the independent second
pass does not support. Do not act on these as originally stated.

| Claim | Verdict | Reason |
|---|---|---|
| `rms()` aliases `out` as the residual buffer | Refuted | The parameters are `(x, residual, weight, out, summed, ...)`, so `out` is `summed`. With `Residual=false` neither is read or written (`kernels.cu:283`, `:301`). |
| FP16 and BF16 conflated in quantize dispatch | Refuted | `kernels.cu:176` tests `kDLBfloat` first. The real residue is the catch-all `float` branch (MNT-02). |
| One-FMA reciprocal refinement breaks FP8 rounding | Refuted, with an assumption | 82,048 exact cases match `__fdiv_rn` bit for bit, assuming `rcp.approx` error ≤ 1 ulp. This cannot be verified from source alone. |
| `__fdividef` loses precision in the gate sigmoid | Refuted | The denominator is in (1,2], so the error is ≤ 2 ulp, below BF16 input resolution. |
| `compiled()` cache has no key | Resolved in EVD-12 remediation | The TVM FFI key includes sources/flags, and the custom compiler flag adds the nvcc path/version; the sidecar binds the remaining build identity for offline reuse. |
| `"memory"` clobber hurts register allocation | Mechanism corrected | It limits load hoisting instead (KRN-06). |
